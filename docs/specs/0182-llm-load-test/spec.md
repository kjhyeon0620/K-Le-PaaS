# LLM 경로 부하 시험(동시 요청 지연·DB 연결·예산 상한 초과량)

## 목적 / 성공 조건
- 목적: LLM을 부르는 요청이 동시에 몰릴 때 서버가 어떻게 되는지는 아직 잰 적이 없다. #174 지표와 #176 사용량 기록은 있지만 한 번에 한 요청씩만 확인했다. 그런데 코드를 읽어 보면 동시성에서 문제가 될 만한 설정이 세 가지 있다.
  1. **open-in-view 기본값(켜짐)**: `spring.jpa.open-in-view`를 설정하지 않아 Spring 기본값이 켜져 있다(로컬 기동 로그에 경고가 있다). 그러면 요청 처음의 사용자 조회에서 얻은 DB 연결을 요청이 끝날 때까지 쥐고 있을 수 있다. 자연어 명령은 LLM 호출 구간을 트랜잭션 밖(`NOT_SUPPORTED`)에 두었지만, 연결은 그대로 쥐고 있을 수 있다. 연결 풀은 Hikari 기본값(10)이다. 이 가설이 맞다면, 응답에 3초 걸리는 LLM 요청이 10개를 넘어 동시에 들어올 때 **LLM과 상관없는 요청까지** DB 연결을 기다린다.
  2. **LLM 호출 제한 시간**: `OpenAiLlmClient`는 SDK 기본값을 쓴다(openai-java 4.80.0 확인: 요청 10분, 연결 1분, 재시도 2회). 공급사가 응답하지 않으면 요청 하나가 Tomcat 스레드와 (가설 1이 맞다면) DB 연결을 수십 분 쥘 수 있다.
  3. **예산 상한은 느슨하다**(#176, 의도된 설계): 검사와 기록 사이에 들어온 동시 요청만큼 상한을 넘을 수 있다. 얼마나 넘는지는 재지 않았다.
- 이 세 가지를 재현할 수 있는 부하 시험으로 확인하고 숫자로 남긴다. 고칠지는 결과를 보고 정한다(Q4).
- 기술적 완료:
  - 부하 스크립트와 가짜 LLM 서버를 저장소에 둔다(`scripts/load/`).
  - 가짜 LLM 서버는 OpenAI 호환 응답을 정해진 지연 뒤에 돌려준다. 지연, 무응답, 오류를 설정할 수 있다.
  - 시나리오별로 지연 분포(p50·p95), 처리량, 실패율, Hikari 대기·활성 연결(관리 포트 지표), 예산 초과량을 낸다.
- 운영: 변경 없음. 운영 서버에는 부하를 걸지 않는다(로컬만).

## 실행 결과 (2026-10-25, 로컬: 패키징 JAR + PostgreSQL 16 컨테이너 + 가짜 LLM, 맥북 한 대)

원자료: `.local/evidence/0182-llm-load-test/`(드라이버 `run.py`, 요약 `summary.md`, 시나리오별 k6 요약·지표 시계열, 스레드 덤프, 누수 감지 로그). 연결 풀 기본 10, 가짜 LLM 지연 3초, 실제 모델 호출 없음.

### S1 동시 자연어 명령 (30초씩 2회)
| 동시 | 성공/요청 (1회 · 2회) | p50 | p95 | Hikari active 최대 | pending 최대 |
|---|---|---|---|---|---|
| 1 | 10/10 · 10/10 | 3.05s | 3.06s | 1 | 0 |
| 5 | 50/50 · 50/50 | 3.04s | 3.06s | 5 | 0 |
| 6 · 8 (원인 확인) | 60/60 · 80/80 | 3.05s | 3.06~3.54s | 6 · 8 | 0 |
| **10** | **0/10 · 1/10** | **33.1s** | 33.1s | 10 | 10 |
| 20 | 1/20 · 0/20 | 31.6s | 33.1s | 10 | 20 |
| 40 | 9/40 · 0/40 | 30.0s | 33.1s | 10 | 40 |

- 동시 8까지는 LLM 지연(3초)만큼 걸리고 모두 성공한다. **동시 10(연결 풀 크기)부터 거의 모두 33초 뒤 500**으로 끝난다. 3초 LLM 대기 뒤 30초 동안 연결을 기다리다가 Hikari 제한 시간(30초)에 실패한다(S1~S4 전체 서버 로그에 `Connection is not available, request timed out after 30000ms` 939회).
- 실패는 느려지는 것이 아니라 **멈춤**이다. 동시 10에서 처리량이 0에 가깝다.

### 원인 확인 (제품 코드 변경 없음)
| 확인 | 결과 |
|---|---|
| 스레드 덤프 (open-in-view 켬, 동시 20, 8초 시점) | 요청 스레드 20개 중 **10개는 `NlpCommandService.processCommand:178`(명령 실행 뒤 `commandLogRepository.save`)에서**, 10개는 `:87`(첫 사용자 조회)에서 연결을 기다린다. LLM을 기다리는 스레드는 0 |
| Hikari 누수 감지 (open-in-view 끔, 동시 10) | 2초 넘게 쥔 연결 10개가 **모두 `ActionDispatcher.executeListRepositories:281`(저장소 조회)에서 얻은 것**이다. 그 스레드들이 다음 `save`에서 두 번째 연결을 기다린다 |
| open-in-view 끔, 동시 10·20·40 | 0/10 · 15/21 · 10/25 성공. **꺼도 같은 멈춤이 생긴다** |
| 지표 시계열: LLM 대기 중 active | open-in-view 켬: active = 동시 수(LLM 3초 동안 연결을 쥠). 끔: LLM 대기 스레드 20개 중 active 0 |

- 판정:
  - **F1 연결 풀 교착(가설에 없던 결함)**: `processCommand`(`propagation = NOT_SUPPORTED`) 안의 저장소 조회가 얻은 연결이 메서드가 끝날 때까지 남고, 그 뒤 `save`는 새 트랜잭션으로 **두 번째 연결**을 요구한다. 풀 크기만큼 요청이 동시에 이 지점에 오면 서로 기다리다 전부 30초 뒤 실패한다. open-in-view와 무관하다. 연결이 남는 정확한 경로(NOT_SUPPORTED 범위의 EntityManager와 Hibernate 연결 유지 방식)는 위 관측에서 추정한 것이고 코드로 확인하지는 않았다. 저장소 조회 외의 LOW 명령 실행도 같은 구조인지는 확인하지 않았다.
  - **가설 1 확인(F2)**: open-in-view가 켜져 있으면 LLM을 기다리는 3초 동안 요청마다 연결 하나를 쥔다. 동시 LLM 요청 수가 연결 풀(10)에 묶인다.
  - 두 결함은 따로다. open-in-view만 끄면 F2는 사라지지만 F1은 남는다.

### S2 부하 중 DB만 읽는 조회 (`GET /llm/usage`, 2 req/s, 30초씩 2회)
| 자연어 동시 | 조회 성공/요청 | 조회 p50 | 조회 p95 |
|---|---|---|---|
| 0 (기준) | 61/61 · 60/60 | 15~17ms | 19~23ms |
| 20 | 35/41 · 33/40 | 22.5~23.1s | 30.0s |
| 40 | 35/41 · 33/40 | 22.1~23.1s | 30.0s |
| 20, open-in-view 끔 | 56/56 | 1.6s | 28.3s |

- LLM과 무관한 조회가 15ms에서 **약 23초로 느려지고 15~18%가 실패**한다. open-in-view를 꺼도 F1의 멈춤 동안 p95가 28초다.
- 기준 2회째의 pending 최대 45는 앞 실행에서 끝나지 않은 요청이 남은 값이다(조회 지연은 정상).

### S3 LLM 무응답 (12건, k6 제한 300초)
- 무응답 요청 12건이 **300초가 지나도 끝나지 않았다**(k6가 끊음). 서버 쪽 제한은 SDK 기본값 10분, 재시도 2회다(가설 2 확인, 10분 이상 기다린 실측은 하지 않음).
- 그동안 DB만 읽는 조회는 **0/52 성공**(모두 30초 뒤 실패)이다. 공급사가 응답하지 않는 요청이 연결 풀 수만큼 쌓이면 LLM과 무관한 API까지 멈춘다(F2 경로).

### S4 예산 상한 (상한 $0.001, 호출당 $0.000152)
| 방식 | 기록된 호출 | 기록된 비용 | 상한 대비 | 200 | 429 |
|---|---|---|---|---|---|
| 순차 15회 | 7 | $0.001064 | 1.06배 | 7 | 8 |
| 동시 10 | 5 | $0.000760 | 0.76배 | 5 | 0 |
| 동시 50 | 9 | $0.001368 | 1.37배 | 9 | 0 |

- 순차는 설계대로 동작한다(상한을 넘긴 호출 1건까지 허용하고 이후 429).
- **동시 요청의 초과량은 잴 수 없었다.** 나머지 요청이 F1으로 실패해서다(동시 50 중 41건 500). open-in-view를 꺼도 같다(동시 10은 0건 기록, 50은 9건 · 1.37배). 기록된 9건 모두 상한 검사를 통과한 뒤 함께 실행됐으므로, 느슨한 상한이 동시 수만큼 넘을 수 있다는 설계(#176)와 어긋나지 않는다. 실제 최대 초과량은 F1을 고친 뒤 같은 시나리오로 잰다.
