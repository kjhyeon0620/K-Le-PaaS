# 신규 장애 주입과 동결 진단 평가 세트

## 목적 / 성공 조건
- 목적: 지금까지의 진단 결과는 모두 규칙과 프롬프트를 고치며 본 개발 세트(`dev` 51)에서 나왔다. #161의 채택 판단(규칙 우선 경로의 제품 반영)은 **모델 점수를 보기 전에 동결한 평가 세트**에서 확인하기로 했다. 비슷한 증상이지만 결론이 달라야 하는 장애를 실제로 주입해 `test` 분할을 만들고, 정답 일치도를 확정해 동결한 뒤 한 번만 측정한다.
- 기술적 완료:
  - `test` 분할 사례 14건(아래 "사례 설계")을 로컬 k3s에서 주입·관측·회복까지 확인해 캡처한다.
  - 정답·근거 묶음([평가 명세](../../eval/diagnosis-eval-spec.md))을 붙이고, 독립 판정 2개(Gemini, 사용자)와의 일치도를 기록한 뒤 manifest 해시로 동결한다(동결 커밋).
  - 동결 커밋 뒤 규칙 단독·`gpt-6-luna`·`gemma4:26b-a4b`(생각 끔)·규칙 우선 정책을 **한 번만** 측정한다(3회 반복).
  - #161 채택 조건으로 규칙 우선 경로의 제품 반영 여부를 판단해 기록한다.
- 운영: 변경 없음 (테스트·문서만). 제품 반영은 결과가 조건을 만족할 때 별도 L 이슈.

## 사례 설계 (측정 전에 고정)
비슷한 증상·다른 결론 3쌍 × 서로 다른 앱 2개 = 12건, 증거 부족 2건, 합계 14건.

| 쌍 | 사례 | 주입 | 예상 관측 | 갈래 | 기대 행동 |
|---|---|---|---|---|---|
| A 실행 형식 | A1 아키텍처 불일치 | ARM64 노드에 amd64 전용 이미지 | `exec format error`, 반복 종료 | `UNSUPPORTED_OBSERVED` | 보류. 아키텍처 불일치는 가설로만(입력에 노드·이미지 아키텍처가 없다) |
| | A2 다른 원인의 실행 형식 오류 | 같은 아키텍처 이미지의 진입점 스크립트에 shebang 없음 | 같은 `exec format error` | `UNSUPPORTED_OBSERVED` | 보류. 아키텍처 불일치를 사실로 단정하면 안 됨 |
| B 종료 | B1 OOMKilled | 메모리 limit을 사용량보다 낮게 | `last_termination_reason=OOMKilled`, exit 137 | `UNSUPPORTED_OBSERVED` | 보류 + OOMKilled를 관측 사실로 설명 |
| | B2 OOM이 아닌 exit 137 | 프로세스가 스스로 SIGKILL로 종료 | `last_termination_reason=Error`, exit 137 | `UNSUPPORTED_OBSERVED` | 보류. OOM을 사실로 단정하면 안 됨 |
| C readiness | C1 잘못된 probe 포트 | probe 포트 ≠ 컨테이너 포트 | probe 포트에서 `connection refused` | `SUPPORTED` (`probe_port_closed`) | 그 원인 + 근거 묶음 |
| | C2 정상 포트, 느린 기동 | probe 포트 = 컨테이너 포트, 앱이 rollout 시간보다 늦게 대기 시작 | 컨테이너 포트에서 `connection refused`, 기동 중 로그 | `UNSUPPORTED_OBSERVED` | 보류. `probe_port_closed`로 단정하면 확신 오답 |
| D 증거 부족 | D1·D2 | 아무 로그 없이 exit 1로 반복 종료 | CrashLoopBackOff, 로그 없음 | `INSUFFICIENT` | 보류 |

- 앱 2개: 쌍마다 서로 다른 앱(공개 이미지 1 + 사내형 셸 이미지 1, 또는 셸 이미지 2)으로 만든다. 로그 형식이 달라야 한 앱의 문구로 맞히는 일을 줄인다.
- 핵심 시험: **규칙이 A·B·C2·D에서 MATCH하지 않는가**(규칙 MATCH 경로 확신 오답 0), **LLM이 C2를 `probe_port_closed`로, B2를 OOM으로 단정하지 않는가**.
- 주입마다 정상 기준 배포 → 주입 → 실패 캡처 → 주입 해제 후 회복 배포 성공까지 확인하고 `injection.recovered`에 기록한다. 기대한 실패가 나지 않으면 사유와 함께 뺀다(뺀 수도 기록).
- 모델 응답을 보고 사례를 넣거나 빼지 않는다.

## 범위
- 포함: 주입용 이미지·캡처 스크립트, 사례 파일(`test` 분할), 정답 일치도 절차와 결과, manifest·CHANGELOG(1.1.0)·DATASET_CARD 갱신, 한 번 측정과 정책 비교, 채택 판단 기록.
- 제외: 제품 코드 변경, 규칙 진단기 수정(측정 뒤 고치면 그 결과는 `dev`로 강등), 설명 채점(3단계), 라벨 추가(OOM 등을 새 라벨로 만들지 않는다).

## 정답 일치도 (모델 측정 전에 끝낸다)
#166 결정의 "작성자 48시간 뒤 재판정"을 아래로 바꾼다(정답은 Claude Code가 붙이므로 사용자 판정이 이미 독립 판정이다. 48시간 대기는 같은 사람의 기억 효과를 줄이려던 것이라 필요 없다).
1. 정답 작성: Claude Code가 판정 가이드로 정답·갈래·근거 묶음을 붙인다. 이 결과는 다른 판정자에게 보이지 않는다.
2. 독립 판정 1: Gemini(다른 계열)에 입력과 판정 가이드만 주고 결론(구체 원인 또는 보류)·갈래·근거를 쓰게 한다. 평가 목적·정답은 알리지 않는다.
3. 독립 판정 2: 사용자가 입력과 판정 가이드만 보고 순서를 섞은 사례에 결론·갈래를 정한다(약 1시간).
4. 세 판정의 일치 건수와 엇갈린 사례를 기록한다. 엇갈리면 판정 가이드를 고치거나 `undecidable`로 둔다. 그 뒤 동결한다.

## 실행 결과

### 캡처 (로컬 실제 클러스터: 패키징 JAR + PostgreSQL 16 + Docker 임시 k3s v1.30.6, rollout 90초, 4개 병렬)
- 14건 모두 의도한 실패로 캡처되고, 기준 설정으로 되돌린 회복 배포가 모두 SUCCESS였다. 뺀 사례 0.
- 관측: 아키텍처 불일치·shebang 없음 모두 같은 `exec /entrypoint.sh: exec format error`(exit 1), OOM은 `last_termination_reason=OOMKilled` exit 137, SIGKILL은 `Error` exit 137과 로그 `Killed`, 잘못된 probe 포트는 probe 포트(8081·9001)에서 연결 거부, 느린 기동은 컨테이너 포트에서 연결 거부와 "rebuilding index: 22% done", 로그 없는 종료는 로그 없이 exit 1.
- 첫 실행은 이미지 import 실패로 멈췄다(에뮬레이션은 `finally`로 복구). 플랫폼을 명시해 저장·import하도록 고쳐 다시 실행했다.

### 정답 일치도 (측정 전)
| 판정 | 구체 원인 일치 | 갈래 일치 |
|---|---|---|
| Claude Code(정답) vs Gemini(`gemini-pro-latest`, 사례마다 별도 호출, 입력과 판정 가이드만) | 14/14 | 14/14 |
| 사용자 | 하지 않음 | 하지 않음 |

### 한 번 측정 (동결 뒤, 14건 × 3회, RAG 없음)
| 모델 | 비용·지연 | 구체 원인 (지원 6회) | 보류 정답 (보류 사례 36회) | 확신 오답 | pass^1 · pass^3 |
|---|---|---|---|---|---|
| `gpt-6-luna` | $0.021 (호출당 $0.0005), 중앙 6.5초 | 6/6 | 33/36 | **3** | 0.929 · 0.857 |
| `gemma4:26b-a4b` (로컬, 생각 끔) | API 과금 없음, 중앙 17.7초 | 6/6 | 34/36 | **2** | 0.952 · 0.929 |

- **확신 오답은 모두 느린 기동 사례**다: 컨테이너 포트에서 연결이 거부되고 로그가 색인 재구성 중인데 `probe_port_closed`로 단정했다(`luna` `ledger-sync` 1/3·`media-indexer` 2/3, `gemma4` `media-indexer` 2/3). `luna`의 한 응답은 요약에 "기동 지연인지 설정 불일치인지는 확인이 필요"라고 쓰고도 라벨을 단정했다.
- 분류 밖 장애(실행 형식 오류 4, OOM 2, SIGKILL 2)와 로그 없는 종료 2에서는 두 모델 모두 30/30 보류했다. 아키텍처 불일치를 사실로 단정했는지, OOM이 아닌 exit 137을 OOM이라 했는지 같은 **설명 문장은 이번에 채점하지 않았다**(3단계 L2).
- 원시 재채점: `luna` 무효 근거 1회, 원시 근거 충분 6/6. `gemma4` 무효 근거 17회(23개 위치), 보류라면서 라벨을 낸 응답 4회, 원시 근거 충분 1/6(컨테이너 포트 미인용, #166과 같은 경향).

### 정책 비교 (저장 응답, 모델 호출 없음, 규칙 v1.2)
| 모델 | 정책 | 지원 사례 정답 | 확신 오답 | 보류 사례 정답 보류 | LLM 호출 |
|---|---|---|---|---|---|
| `gpt-6-luna` | 규칙 단독 / LLM 단독 / 규칙 우선 | 6 / 6 / 6 | **0 / 3 / 3** | 36 / 33 / 33 | 0 / 42 / 36 |
| `gemma4` | 규칙 단독 / LLM 단독 / 규칙 우선 | 6 / 6 / 6 | **0 / 2 / 2** | 36 / 34 / 34 | 0 / 42 / 36 |

- 규칙은 잘못된 probe 포트 2건만 MATCH(정답)했고 나머지 12건은 모두 NO_MATCH였다. 느린 기동(컨테이너 포트 거부)·SIGKILL(이전 readiness 거부 이벤트 포함)에서도 MATCH하지 않았다.
- 규칙이 정하지 못한 12건에서 LLM이 더한 해결은 없다(보류가 정답인 사례를 보류했을 뿐이고, 규칙 단독도 보류한다). LLM이 더한 것은 확신 오답 2~3회다.

## 채택 판단
- **#161 조건**: ① 규칙 MATCH 경로의 확신 오답 0 — 충족(MATCH 2건 × 3회 모두 정답). ② 규칙 우선이 LLM 단독보다 확신 오답이 늘지 않음 — 충족(같음).
- 따라서 **규칙 우선 경로는 제품 반영 조건을 만족**한다. 반영은 별도 L 이슈로 한다.
- 다만 이 세트에서 규칙 미해결 사례의 **LLM 라벨 단정은 이득 없이 위험만 더했다**. #161 결정대로 "규칙이 MATCH하지 않으면 LLM은 라벨을 단정하지 않고 관측·가설만 쓴다"(또는 LLM 라벨 단정에 라벨 전제 조건 검사를 건다)를 제품 반영 이슈의 선택지로 올린다. 이 선택지는 이 세트의 결과를 보고 나온 것이라, 고른 방식은 **새 동결 세트로 다시 확인**해야 한다.
- 분류 밖 장애에서 LLM의 가치(관측을 정확히 설명하는가)는 이번에 재지 않았다. LLM을 진단에서 빼자는 결론이 아니라 "라벨 결정은 규칙, 설명은 LLM"으로 역할을 나누는 근거다.
- 표본 한계: 에피소드 14건(같은 쌍의 두 앱은 독립이 아님). 규칙이 MATCH하면 안 되는 12건에서 잘못된 MATCH 0이어도 단측 95% 상한 약 22%, MATCH 경로 자체는 2건뿐이다. 사례·정답 작성자가 같고 사람 판정이 없다.

## 범위 밖, 후속 후보
- 규칙 우선 진단의 제품 반영(L): MATCH면 LLM 호출 없이 규칙 결론, 아니면 LLM은 관측·가설 위주. 결정 기록·반례 테스트·MATCH 시 LLM 호출 0 테스트 포함.
- 라벨 전제 조건 서버 검사: 예) `probe_port_closed`인데 거부된 포트가 컨테이너 포트면 보류로 바꿈. 서버의 근거 위치 검증과 같은 자리. 이 세트를 본 뒤 나온 생각이라 새 동결 세트로 확인.
- 설명 채점(L2): 사람 판정 50개를 할지 먼저 정한다(이번에 사람 판정을 하지 않았으므로 판정자 신뢰도를 세울 근거가 없다).

## 측정 계획 (동결 뒤 한 번)
- 모델: `gpt-6-luna`(기본), `gemma4:26b-a4b`(로컬, 생각 끔). 각 사례 3회. RAG 없음.
- 정책: 규칙 단독(v1.2) / LLM 단독 / 규칙 우선.
- 지표: 확신 오답(원시·보정 후), 보류 정밀도·재현율, 구체 원인, 근거 충분, pass^k, 비용·지연. 갈래별 건수로 보고하고 사례 단위로 해석한다.
- 예상 시간: `luna` 수 분·수 센트, `gemma4` 14건 × 3회 × 15~20초 ≈ 15분(메모리 약 16GB, 끝나면 `ollama stop`).

## 채택 판단 (측정 전에 고정, #161)
- 규칙 우선의 제품 반영 조건: ① `test`에서 규칙 MATCH 경로의 확신 오답 0, ② 규칙 우선이 LLM 단독보다 확신 오답이 늘지 않음.
- LLM이 규칙 미해결 사례에서 추가로 해결하는지(보류 정답 포함)도 함께 본다. 추가 해결이 없으면 LLM 경로를 기본에서 빼는 것도 검토 대상으로 기록한다.
- 표본 한계를 함께 쓴다: 확신 오답 0이어도 14건이면 단측 95% 상한 약 19%(같은 쌍의 두 앱은 완전히 독립이 아니다).
