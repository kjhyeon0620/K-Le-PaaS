# 저장된 진단 응답 재채점으로 평가 회귀 게이트

## 목적 / 성공 조건
- 목적: 진단 평가 결과는 지금 손으로 재계산 모드(`DIAGNOSIS_EVAL_RAW`·`_POLICY`)를 돌려야 확인된다. 저장된 원문은 `.local/`(git 제외)에만 있어 CI는 볼 수 없다. 그래서 응답 검증(`DiagnosisPrompt.parse`), 라벨, 채점기, 정답·근거 묶음, 규칙을 바꾸는 PR이 기존 평가 결과를 바꿔도 아무도 모른다. 기준 실행의 모델 원문을 저장소에 두고, 모델을 부르지 않고 매 PR마다 다시 채점해 결과가 바뀌면 실패하게 한다.
- 기술적 완료:
  - 기준 실행 원문(모델 응답 텍스트만, 사례 입력은 이미 저장소에 있음)을 `backend/src/test/resources/diagnosis-eval/baselines/`에 둔다.
  - 회귀 테스트가 기준마다 지금 코드로 원시 계약(L0)·정답(L1)·근거 충분·정책 비교(규칙 단독/LLM 단독/규칙 우선)를 계산하고, 저장된 기대 요약(스냅숏)과 같은지 본다. 다르면 표를 출력하고 실패한다.
  - 기대 요약을 바꾸려면 쓰기 모드로 다시 만들고 변경 이유를 데이터셋 CHANGELOG에 적는다(차이가 PR diff에 그대로 보인다).
  - CI 실행 결과 표를 PR의 작업 요약(job summary)에 붙인다(Q3).
- 운영: 변경 없음 (테스트·CI만).

## 범위
- 포함: 기준 원문 추출 스크립트, 기준 파일, 회귀 테스트와 쓰기 모드, 기대 요약, 데이터셋 manifest·CHANGELOG 갱신, CI 요약 출력(Q3), 문서, 스펙 0170 운영 반영(#171 배포·운영 확인 결과).
- 제외: 실제 모델 호출 평가의 CI 실행(비용·키가 필요해 수동 유지), 자연어 명령 회귀(Q4), 설명 채점, 품질 기준선(임계값) 판정.

## 입출력·계약
- 기준 파일(사례 묶음별 JSON): `{baseline_id, case_set, dataset_version, model, prompt_version, measured_at, source(스펙 번호), runs: {case_id: [raw, ...]}}`. 원문 외 사용량·지연은 넣지 않는다.
- 기대 요약(`baselines/expected.json`): 기준마다 호출 수, JSON 실패, 라벨 목록 밖, 무효 근거 호출·위치, 보류인데 라벨, 원시 단정, 원시 확신 오답, 원시 구체 원인 정답, 서버 보정 후 구체 원인 정답·확신 오답, 원시 근거 충분, 정책별(규칙 단독·LLM 단독·규칙 우선) 지원 정답·확신 오답·LLM 호출. 사례별 결과는 넣지 않는다(요약이 같으면 통과, 다르면 사례별 차이를 출력).
- 프롬프트 버전 불일치: 기준의 `prompt_version`이 지금 `DiagnosisPrompt.VERSION`과 다르면 실패하고 "새 기준 실행이 필요"라고 알린다(Q2).
- 쓰기 모드: `DIAGNOSIS_BASELINE_WRITE=1`일 때만 기대 요약을 다시 쓴다.

## 권한·안전
- 해당 없음(테스트·CI). 기준 원문은 가린 입력에 대한 모델 출력이고 비밀값이 없다. 저장소는 공개이므로 넣기 전에 비밀값 패턴 검사를 한다.

## 제약
- 참조: [평가 명세](../../eval/diagnosis-eval-spec.md), #159(원시 재채점), #161(정책 비교), #166(근거 충분), #168(동결 세트)
- 재채점은 기존 `RawDiagnosis`·`DiagnosisPrompt.parse`·`DiagnosisEval`·`SignatureRules`를 그대로 쓴다. 새 채점 규칙을 만들지 않는다.
- 기준 실행은 이미 측정한 결과에서 뽑는다. 새 모델 호출은 하지 않는다.
- `test` 분할 기준(#168)은 정답을 바꾸면 dev로 강등되는 규칙을 그대로 따른다. 회귀 게이트가 정답 변경을 드러내는 역할을 한다.
