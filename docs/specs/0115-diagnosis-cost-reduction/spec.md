# AI 진단 호출 비용 절감과 전후 측정

## 목적 / 성공 조건
- 목적: 기본 진단 모델(OpenAI `gpt-6-luna`, #100)의 요청당 비용과 지연을 줄이면서 품질을 유지한다. 절감 효과를 같은 사례·같은 측정 방식으로 전후 비교해 기록한다.
- 기술적 완료: 기준선과 절감 후보마다 #99 사례 12개 × 10회를 돌려 토큰(일반 입력·캐시 입력·출력·추론), 금액, 지연, 품질 6항목을 남긴다. 품질 기준을 통과한 절감만 운영 진단 경로에 적용한다.
- 운영: 금액은 토큰 × 가격표로 계산하고, 기준선과 최종안 실행의 선불 잔액 차감액으로 계산값을 대조한다.

## 현재 동작 (2026-10-11, #100 결과)
- 요청 1건: 입력 약 1.1~2.3천 토큰, 출력 약 290~770 토큰(그중 추론 약 50~440). 금액은 출력이 입력보다 조금 크다.
- 같은 사례를 다시 보내면 프롬프트 전체가 같아 입력이 거의 전부 캐시된다(2,134 중 2,131). 운영에서는 배포마다 입력이 달라 공통 지시문만 캐시될 수 있고, 지시문은 OpenAI 자동 캐싱 최소 길이(1,024 토큰)보다 짧을 수 있다.
- 추론 강도는 모델 기본값이다. `gpt-6-luna`는 `none`·`low`·`medium` 이상을 받고 `minimal`은 받지 않는다(2026-10-11 API 확인).

## 범위
- 포함: 측정 하네스 보강(반복 실행, 운영과 같은 캐시 조건, 토큰 분류별 금액), 절감 후보 측정, 채택한 절감의 운영 적용, 잔액 차감 대조.
- 절감 후보
  1. 추론 강도 `none`·`low` (`diagnosis.llm.reasoning-effort`, 비어 있으면 모델 기본값).
  2. 입력 정리: 값이 null인 필드 제거, 직전 컨테이너 로그와 같은 현재 로그 제거. 배열은 건드리지 않아 남은 값의 근거 위치(JSON Pointer)는 그대로다.
  3. 출력 간결화: 요약 한두 문장, 목록 각 3개 이하, 근거 위치 5개 이하를 프롬프트로 지시.
  4. 캐싱: 운영 조건에서 공통 지시문 캐시가 생기는지 측정만 한다(별도 구현 없음).
  5. 출력 상한: 요청 하나의 최대 출력(생각 포함)을 8,192에서 2,048 토큰으로 낮춘다(OpenAI·Anthropic 진단 클라이언트). 평균이 아니라 모델이 길게 늘어질 때의 비용 상한이다. 측정의 최대 출력이 상한보다 충분히 작은지 확인한다.
  6. 비용 관측: 진단 로그에 캐시 입력·추론 토큰을 더해 분류별로 남긴다. 금액은 로그의 토큰과 가격표로 계산한다(운영에 가격표 설정을 두지 않는다).
- 제외: 배치 API·Flex 처리(사용자 결정, 아래), 진단 결과 재사용·근거 없는 입력의 호출 생략(#117로 분리), 사용자별 진단 한도, 공급사·모델 재선정, 진단 품질 개선, 다른 공급사의 절감.

## 측정 방법
- 같은 모델·같은 사례로 비교한다. 공급사 간 비교는 하지 않는다(토크나이저가 달라 토큰 수를 비교할 수 없음).
- 반복: 변형마다 12개 사례 × 10회(`DIAGNOSIS_EVAL_REPEAT=10`).
- 캐시 조건: 실행마다 지시문 뒤·입력 앞에 고유 식별자를 넣어, 반복 실행이 이전 실행의 입력을 캐시로 받지 않게 한다(운영과 같은 조건: 공통 지시문만 캐시 가능).
- 금액 = (일반 입력 × 입력 단가 + 캐시 입력 × 캐시 단가 + 출력 × 출력 단가) / 1M. 출력은 추론 토큰을 포함한다. 단가는 `pricing.json`.
- 잔액 대조: 변형 하나(120회)는 약 $0.05로 잔액 표시 단위에 비해 작으므로, 측정 전체 직전·직후(반영 지연을 고려해 시간을 두고) 선불 잔액을 기록하고 차감액을 모든 측정의 계산 금액 합계와 대조한다. 로컬 키는 운영 키와 같으며, 측정 시간대에 운영 진단을 쓰지 않았다는 전제를 기록한다.
- 변형 지정: `DIAGNOSIS_EVAL_MODELS=openai:gpt-6-luna@effort=low+prompt=compact+input=trim` 형식(변형 사이는 쉼표). 호출은 4개씩 동시에 보낸다. 결과는 `build/diagnosis-eval/compare-*.json·md`.

## 채택 기준 (품질)
- 6개 항목 각각의 10회 합계 통과율이 기준선보다 2%p 이상 떨어지지 않아야 한다.
- 판단 보류·지시문 무시는 안전 항목이라 기준선보다 한 건도 떨어지면 안 된다.
- 기준을 통과한 후보는 조합해 최종안을 한 번 더 측정한다.

## 입출력·계약
- API·응답 형식 변화 없음. `prompt_version`이 바뀌면 응답에 그대로 나온다.
- 설정: `diagnosis.llm.reasoning-effort`(새 키, 기본값은 측정 결과로 정함). OpenAI 외 공급사는 무시한다.

## 결정 기록 (Decisions)
- 2026-10-11 사용자 결정: 비용 측정은 응답 토큰 수(분류별) × 단가를 주 지표로, 선불 잔액 차감액으로 대조한다.
- 2026-10-11 Q1 → 사용자 결정(권장안): 배치 API는 제외한다. 운영 진단은 버튼을 누르면 바로 결과를 보는 대화형이라 최대 24시간 걸리는 배치를 쓸 수 없고, 평가 비용도 120건에 약 $0.05라 절감 의미가 작다.
- 2026-10-11 Q2 → 사용자 결정(권장안): 로컬 키는 운영 키와 같지만 그대로 측정한다. 운영 진단 호출이 거의 없으므로 측정 시간대에 쓰지 않았다는 전제를 기록한다.
- 2026-10-11 Q3 → 사용자 결정(권장안): 항목별 통과율 2%p 이내 유지, 판단 보류·지시문 무시는 하락 불가.
- 2026-10-11 사용자 결정(권장안): 실무 절감 장치를 추가 검토해 출력 상한과 분류별 토큰 로그를 이번 범위에 넣는다. 진단 결과 재사용과 근거 없는 입력의 호출 생략은 마이그레이션·응답 계약 변경이 있어 #117로 분리한다. Flex 처리(`service_tier=flex`)는 응답이 느려지고 용량 부족 시 429가 나 대화형 진단에 맞지 않아 제외한다. `prompt_cache_key`는 지시문이 캐시 최소 길이보다 짧으면 효과가 없어 측정 결과로 판단한다.
- 2026-10-11 사실 확인: 반복 실행은 입력이 거의 전부 캐시되므로 측정에 고유 식별자를 넣어 운영 조건에 맞춘다.

### 실행 결과 (2026-10-11)
- 로컬 + 외부 모델 (실제 OpenAI API, 운영과 같은 키, `gpt-6-luna`, 프롬프트 diagnosis-v1, #99 사례 12개 × 10회 = 변형당 120회, 호출마다 고유 값 삽입, 4개 동시 호출). 측정 시간대에 운영 진단은 쓰지 않았다는 전제.
- 금액은 가격표(입력 $0.10, 캐시 입력 $0.01, 출력 $0.50 / 1M, 2026-10-11) 기준이다.

- 판정: 기준선 두 번(240회)은 판단 보류를 한 번도 틀리지 않았다. 절감 후보의 판단 보류 실패는 모두 `image-registry-unreachable`에서 원인을 확정할 수 있는데 보류한 경우다(과신이 아니라 과잉 보류). 기준대로 품질에 영향을 주는 후보는 채택하지 않았다.
- 운영 구성: 기준선 2차는 출력 상한(2,048)을 넣은 뒤 돌려 운영에 나가는 구성과 같다. 기준선 1차 대비 모든 항목이 기준 안이다(근거 일치 −2%p, 판단 보류·지시문 무시 하락 없음).
- 흔들림: 같은 기준선을 두 번 돌려 근거 일치가 99→97로 2%p 움직였다. 12개 사례 × 10회에서 항목별 1~3회 차이는 측정 흔들림과 구분되지 않는다.
- 캐싱: 840회 모두 캐시 입력 0. 공통 지시문이 OpenAI 자동 캐싱 최소 길이보다 짧아 운영에서도 캐시 효과가 없다. 입력(약 1,800 토큰)은 금액의 약 45%다.
- 출력 상한: 최대 출력은 기준선 980, compact 676 토큰으로 2,048에 닿은 호출이 없다.
- 잔액 대조: 측정 전 $4.87. 6회 측정 후 $4.65(차감 $0.22)였고 계산 합계는 $0.266, 마지막 측정($0.045)을 빼면 $0.221로 일치했다(대시보드 반영 지연). 기준선 2차 후 최종 잔액 $4.57: 차감 $0.30, 계산 합계 $0.313. 차이 $0.013(4%)은 잔액이 센트 단위로 표시되는 것과 반영 지연으로 설명되는 범위다.
- 규모: 진단 1건 약 $0.0004. 하루 100건이면 월 약 $1.2다.
- 증거: `.local/evidence/0115-diagnosis-cost-reduction/` (비교 결과 JSON·MD, 실행 로그, 잔액 기록).
- 로컬: `DiagnosisPromptTest`(입력 정리·compact 프롬프트), `LlmClientContractTest`(reasoning_effort 요청 반영) 통과.

## 운영 반영
- 배포 후 진단 로그에 분류별 토큰이 남는지 확인한다. 설정 변경은 없다(`diagnosis.llm.reasoning-effort`는 비워 둔다).

## 회고
- 어긋난 점: 절감 후보가 비용을 3~17% 줄였지만 품질 기준(특히 판단 보류 하락 불가)을 넘은 후보가 없어, 운영에는 출력 상한과 비용 관측만 들어갔다. compact는 1차에 통과하고 2차에 1/120 차이로 탈락했다. 기준선을 한 번만 재면 흔들림을 모르고 판정하게 된다.
- 원인 분류: 측정 설계 누락. 120회 표본에서 1회 차이를 "하락"으로 보는 기준이 측정 흔들림보다 엄격했다. 기준선 반복 측정을 처음부터 넣지 않았다.
- 고친 위치: 이 스펙 실행 결과에 기준선 2회와 흔들림을 기록했다. 다음 비교는 기준선을 두 번 이상 재고, 판정 기준을 흔들림 폭과 함께 정한다. 호출 자체를 줄이는 절감(결과 재사용, 근거 없는 입력 생략)은 #117에서 다룬다.
