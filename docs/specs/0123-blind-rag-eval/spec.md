# 독립 작성 평가 세트로 RAG 진단 효과 측정

## 목적 / 성공 조건
- 목적: #104 RAG 평가는 시스템을 만든 쪽이 답을 알고 사례를 만들었다. 다른 계열 모델이 독립적으로 쓴 자료로 평가 세트를 만들고, 조정용·평가용을 나눠 RAG 효과를 다시 잰다.
- 완료: 생성 원문·프롬프트·재현 사례·분할이 저장돼 있고, 평가용 세트를 시스템·기준값 고정 뒤 한 번만 측정해 RAG 있음/없음 결과와 한계를 기록한다.

## 원칙 (생성 전에 고정)
1. 작성자: Gemini(`gemini-pro-latest`, 응답의 실제 모델 버전을 기록)가 쓴다. 시스템을 만든 모델(Claude)·진단 모델(OpenAI GPT)과 다른 계열이다.
2. 정보 분리: 사내 서비스 명세, runbook, 기준 설정, 실패 시나리오를 서로 다른 API 호출(대화 문맥 없음)로 만든다. 실패 시나리오 작성자는 runbook을 보지 않는다. 어떤 호출에도 RAG·평가 목적·시스템 내부를 알리지 않는다.
3. 프롬프트는 아래에 고정하고 결과를 본 뒤 바꾸지 않는다. 응답 원문은 자동 저장하고 형식 변환은 스크립트로만 한다. 응답이 JSON으로 읽히지 않으면 같은 프롬프트로 다시 호출하고 그 사실을 기록한다.
4. 골라 쓰지 않는다. 생성된 시나리오는 전부 쓰고, 플랫폼으로 재현할 수 없거나 기대한 실패가 나지 않으면 이유와 함께 뺀다(뺀 비율도 결과에 적는다).
5. 정답 라벨은 시나리오의 넣은 결함에서 정해진다. 재현하는 쪽이 라벨을 바꾸지 않는다.

## 생성 (Gemini API)
- G1 사내 서비스 명세 3개: 업무 영역만 다르게(결제 정산 / 재고 동기화 / 알림 발송) 별도 호출. JSON 명세(이름, 역할, 포트, HTTP 헬스 경로, env 목록, 기동 실패 조건과 로그 줄·오류 코드, 정상 로그).
- G2 runbook 8개: 공개 이미지 5개(redis:7-alpine, postgres:16-alpine, mysql:8.0, eclipse-mosquitto:2.0, influxdb:2.7-alpine) + 사내 서비스 3개, 서비스마다 별도 호출. 사내 서비스는 그 명세만 준다.
- G3 기준 설정 1회: 8개 서비스의 정상 배포 설정.
- G4 실패 시나리오 3회(각 24개, 총 72개): 서비스 목록, 사내 서비스 명세, 기준 설정, 바꿀 수 있는 설정, 원인 목록만 준다. 회마다 다른 서비스 순서로 준다. 시나리오마다 바꾼 설정(기계적으로 적용할 수 있는 JSON), 원인 라벨, 흔한 정도, 고치는 방법.
- 바꿀 수 있는 설정(플랫폼이 재현 가능한 것만): 이미지, 환경 변수(이름=값), 컨테이너 포트, 레플리카 수, readiness probe(HTTP 경로·포트 또는 없음), CPU·메모리 requests.

## 재현 (로컬 k3s)
- 패키징 JAR + PostgreSQL + Docker 임시 k3s v1.30.6. 공개 이미지는 로컬에 있는 것을 import한다(새 다운로드 없음). 사내 서비스는 명세대로 셸 스크립트 이미지(`FROM redis:7-alpine`, busybox `nc`)로 구현한다.
  - 옮기는 규칙(기계적): 선택 env 기본값 채움 → `startup_logs` 첫 줄(기동 배너) → `startup_failures`를 명세 순서대로 검사해 첫 실패에서 `log_line`(stderr)·`exit_code` → 나머지 `startup_logs` → `ready_log` → 포트(이름이 PORT로 끝나는 env가 숫자면 그 값)에서 모든 HTTP 요청에 200. 정상 로그를 모두 검사 전에 찍으면 실패하는 컨테이너가 "환경 변수가 유효하다"는 줄 뒤에 FATAL을 찍는 모순이 생겨, 측정 전에 이 순서로 정했다.
- 시나리오마다 저장소 하나: 기준 설정으로 성공 배포 → 시나리오 변경 적용 → 실패 배포를 캡처(상세·로그 API 응답, #99와 같은 형식). rollout 타임아웃 90초.
- 실패하지 않거나 기대와 다른 실패 종류(예: 기준 설정 자체 실패)는 제외하고 사유를 남긴다.

## 분할 (시드 123, 재현 성공 사례만)
- 사례를 서비스별로 묶어 섞은 뒤 서비스마다 20% 과거 사건, 20% 조정용, 60% 평가용(반올림, 서비스당 최소 1개 평가용).
- 과거 사건: 시나리오의 원인 라벨과 고치는 방법으로 서버와 같은 사건 글(`KnowledgeService.incidentText` 형식)을 만든다. 같은 서비스의 사례에서만 검색된다.
- 지식 범위: 사례마다 그 서비스의 runbook, 그 서비스의 과거 사건, 플랫폼 runbook 4개.

## 측정
- 조정용: 기준값 후보 0.35·0.45·0.55를 RAG 있음 × 2회로 돌려 구체 원인 통과율이 가장 높은 값(같으면 0.45)을 고른다. 시스템·프롬프트는 바꾸지 않는다.
- 평가용: 고른 기준값으로 RAG 없음/있음 × 3회, 한 번만 측정한다.
- 지표: 범주·구체 원인 통과율(사례 수 기준 95% 신뢰구간 함께), 판단 보류 비율, 잘못된 단정 비율(보류하지 않고 틀린 원인), 근거 유효, 검색 적중(그 서비스 runbook 또는 같은 원인의 과거 사건이 상위 k에 있음), 지식 근거(그것을 인용), 공개 이미지·사내 서비스로 나눈 결과, 호출당 비용·지연.
- RAG가 도움이 안 되거나 나빠진 결과도 그대로 기록한다.

### 실행 결과 (2026-10-11)
- 생성: Gemini `gemini-pro-latest` → 실제 `gemini-3.1-pro-preview`, 15회 호출 모두 첫 시도에 JSON으로 읽힘, 약 9.2만 토큰(약 $1). 사내 서비스 3개(정산 계산기, 재고 정렬기, 알림 푸시 노드), runbook 8개, 기준 설정 8개, 시나리오 72개(원인 6종 × 12).
- 재현 (로컬 실제 클러스터: 패키징 JAR + PostgreSQL 16 + Docker 임시 k3s v1.30.6, 4개 병렬): 72개 중 71개 캡처. 제외 1개(`g1-sac-prb-port`): 시나리오가 `container_port`만 바꾸면 앱이 그 포트를 연다고 가정했으나, 이 값은 Kubernetes 메타데이터라 앱은 기존 포트에서 듣고 probe도 기존 포트로 가서 배포가 성공했다. 넣은 결함과 실패 종류는 모두 대응했다(이미지 → IMAGE_PULL 24, CPU → UNSCHEDULABLE 12, env → CRASH_LOOP 12, probe → READINESS_TIMEOUT 23).
- 첫 재현 실행은 병렬 저장소 생성이 도메인 고유 제약(빈 값)에 걸려 중단했고, 스크립트를 고쳐 처음부터 다시 돌렸다(중단분은 `aborted-run-1/`).
- 분할(시드 123): 과거 사건 16, 조정용 16, 평가용 39 (공개 이미지 25, 사내 서비스 14).
- 조정용 (RAG 있음 × 2회): 기준값 0.35 → 구체 원인 30/32, 0.45 → 30/32, 0.55 → 31/32. 규칙대로 0.55를 골랐다(차이 1회로 흔들림 수준).
- 평가용 (39개 × 3회, 기준값 0.55, 한 번만 측정):

| 변형 | 구체 원인 (95% CI) | 범주 | 판단 보류 | 잘못된 단정 | 사례 다수결 정답 | 검색 적중 | 지식 근거 | 호출당 USD | 지연 중앙값 ms |
|---|---|---|---|---|---|---|---|---|---|
| RAG 없음 | 116/117 (99%, 95–100%) | 116/117 | 1/117 | 0/117 | 39/39 | - | - | 0.000428 | 4,522 |
| RAG 있음 | 114/117 (97%, 93–99%) | 116/117 | 1/117 | 2/117 | 38/39 | 81/117 | 53/117 | 0.000531 (+24%) | 4,924 |

  - 공개 이미지: 없음 74/75 → 있음 72/75. 사내 서비스: 둘 다 42/42.
  - 차이는 `g1-mq-prb-proto` 하나다. 시나리오 라벨은 probe_protocol_mismatch(MQTT 포트에 HTTP probe)지만, mosquitto 2.0 기본 설정은 로컬 전용 모드라 Pod IP로 1883을 열지 않아 probe가 `connection refused`로 실패했다(관측상 포트 닫힘). runbook이 로컬 전용 모드를 설명했고, RAG 있음은 이를 근거로 probe_port_closed라고 답했다. 원칙대로 라벨을 바꾸지 않고 채점했다(라벨이 관측과 맞지 않는 사례로 기록).
- 결론: 독립 작성 세트에서는 RAG의 측정 가능한 개선이 없었다. 지식 없이도 99%를 맞혔다. 실패 원인이 로그·이벤트·직전 성공 대비 변경(env 이름 삭제, 이미지·probe·CPU 변경)에 직접 드러나고, 공개 이미지는 진단 모델이 이미 알며, 사내 서비스도 로그에 env 이름을 적기 때문이다. #104의 개선(15/25 → 25/25)은 로그에서 단서를 지운 사례에서만 나타났다. RAG는 로그가 원인을 말하지 않는 앱(앱 고유 오류 코드 등)에서만 효과가 있을 것으로 보이며, 독립 작성 세트에는 그런 사례가 거의 없었다.
- 비용: 측정(조정 96회 + 평가 234회) 약 $0.18, 생성 약 $1. 합계 2,000원 안팎.
- 한계: 시나리오는 LLM이 설계했고 실제 장애가 아니다. 사내 서비스 구현과 재현은 시스템을 만든 쪽이 기계적 규칙으로 했다. 반복 3회는 독립 표본이 아니다(사례 39개 기준으로 볼 것).
- 로컬: `DiagnosisEvalTest` 5개(독립 세트 형식·분할 겹침 없음 포함).
- 증거: `.local/evidence/0123-blind-rag-eval/` (프롬프트 입력·응답 원문 `raw/`, 생성 결과 `generated/`, 사내 서비스 이미지, 캡처, 생성·빌드·캡처·변환·집계 스크립트, 비교 결과, `analysis.txt`).

## 회고
- 어긋난 점: 독립 평가로 #104의 개선 수치가 사례 설계에서 나온 것임이 확인됐다. 생성된 실패는 대부분 로그·변경 내역에 원인이 드러나 RAG가 필요 없었다. 시나리오 2개는 생성 모델의 가정이 실제 동작과 달랐다(container_port 의미, mosquitto 로컬 전용 모드).
- 원인 분류: 평가 설계 — 가공 사례만으로 효과를 주장했다(#104). 생성 모델은 교과서적 실패를 만들고 플랫폼 동작을 다 알지 못한다.
- 고친 위치: #104 결과를 이 측정으로 보완해 product.md에 RAG 효과의 범위를 적었다. 이 결과로 운영 진단의 RAG를 기본으로 껐다(#129). 이후 RAG 개선은 로그만으로 원인을 알 수 없는 실제 사례(#105 실증 등)를 먼저 모은 뒤 판단한다.
