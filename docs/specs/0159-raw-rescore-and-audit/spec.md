# test: 진단 정답 감사와 원시 응답 재채점

## 목적 / 성공 조건
- 목적: 지금까지의 진단·자연어 평가 수치가 무엇을 증명했는지 정정한다. 모델 원시 출력의 품질과 서버 보정 장치의 효과를 분리하고, 정답 자체의 오류를 찾는다.
- 기술적 완료: 저장된 결과의 모델 원문으로 원시 지표를 다시 계산하는 모드(모델 호출 없음)와 단위 테스트, 저장 결과 전체의 원시/보정 후 표, 기존 51사례의 정답 감사표.
- 운영: 변경 없음 (테스트·문서만).

## 현재 동작 (2026-10-22 코드 확인)
- `DiagnosisPrompt.parse()`: 코드 블록을 벗기고 JSON을 읽는다. 목록 밖 범주·구체 원인은 지우고, 입력에 없는 근거 위치는 버리며, `abstain=false`인데 범주·원인·근거 중 하나라도 없으면 보류로 바꾼다. 보류면 라벨을 지운다. 범주-구체 원인 관계는 확인하지 않는다.
- 진단 하네스(`DiagnosisModelComparisonTest`)는 위 결과로 채점한다. 결과 JSON의 각 호출에 `raw`(모델 원문), `diagnosis`(보정 후), `score`가 있다. 호출 실패는 보류로 채점된다.
- `IntentParser`: 코드 블록이나 문장 속 `{...}`를 추출하고, intent를 대문자로 바꿔 enum에 없으면 `UNKNOWN`, `args`·`confidence`·`message`가 없으면 기본값을 넣는다.
- 저장 결과(`.local/evidence/`): #100 4개, #115 3개, #123 4개(평가용 1개), #152 2개, #154 1개, #136 1개, #58 2개.

## 범위
- 포함:
  - **진단 원시 재채점**(`DIAGNOSIS_EVAL_RAW=<compare json>`): 저장된 `raw`를 서버 규칙 없이 다시 읽어 호출마다 아래를 판정한다.
    - 계약: JSON 읽기, 라벨이 목록 안, 범주-구체 원인 관계(구체 원인 설명의 범주 접두어), 근거 위치가 입력에 있음(지식 위치 `/knowledge/i`는 그 사례의 검색 결과 수로 판정), 보류인데 라벨을 낸 경우.
    - 원시 결정: 보류하지 않고 구체 원인을 냈으면 "단정". 단정이 틀렸거나 보류가 정답인 사례에서 단정했으면 **원시 확신 오답**.
    - 서버 효과: 서버가 보류로 바꾼 호출 수와, 그 원시 단정이 맞았는지·틀렸는지.
    - 원시 근거: 원시 인용 위치가 정답 근거 중 하나와 일치하는지(최소 충분 근거 묶음은 2단계).
  - **자연어 원시 계약**(`NLP_EVAL_REPLAY` 결과에 열 추가): 코드 블록·문장 속 추출이 필요했던 호출, intent 누락·enum 밖(파서가 UNKNOWN으로 바꿈)·소문자, `args`·`confidence` 누락.
  - **51사례 정답 감사**: #99 12 + #123 평가용 39. 상태 `유지 / 정정 / 복수 답 허용 / 판정 불가`, 주입 의도와 입력으로 입증되는 결론, 근거. 감사표는 이 스펙에 둔다.
- 제외: 감사 결과를 정답 파일에 반영하는 변경(감사표 확정 후 별도 커밋 또는 이슈), 새 모델 호출, 시그니처 규칙 진단기(다음 이슈), L2 설명 채점, 최소 충분 근거 묶음 정의.

## 결정 기록 (Decisions)
- 2026-10-22 원시 재채점은 저장된 `raw`만 쓰고 모델을 다시 부르지 않는다. `input=trim` 변형은 입력 구조가 달라 근거 위치 판정에서 제외하고 사유를 표에 적는다. 기본값으로 가정.
- 2026-10-22 범주-구체 원인 관계는 `DiagnosisLabels.ROOT_CAUSES` 설명의 접두어(`IMAGE:` 등)로 판정한다. 기본값으로 가정. (서버는 이 관계를 검사하지 않으므로 원시 계약 위반으로만 센다)
- 2026-10-22 정답 감사는 이 작업에서 AI(Claude Code)가 1차 판정하고 근거를 남긴다. 사람(저장소 소유자)의 재검토 전까지 "1차 감사"로 표시한다. 감사 결과로 기존 수치를 바꾸지 않고, 정정 후 수치는 정답 파일 반영 뒤 따로 낸다.
- 2026-10-22 자연어 원시 계약은 `IntentParser`가 받아 주는 것(대소문자, 코드 블록)도 "보정"으로 센다. 실패로 세지 않고 별도 칸에 둔다.

## 정답 감사 (1차, 2026-10-22, Claude Code)
기준: 정답 라벨이 **입력으로 입증되는 결론**과 맞는가. 주입 의도(`notes`·`provenance`)와 관측(이벤트·로그·Pod 상태·설정)을 대조했다. 사람 재검토 전까지 1차다.

| 상태 | 사례 수 | 사례 |
|---|---|---|
| 유지 | 50 | #99 12개 전부, #123 평가용 38개 |
| **정정 제안 (복수 답 허용)** | 1 | `g1-mq-prb-proto` |
| 판정 불가 | 0 | - |

**`g1-mq-prb-proto`**: 주입 의도는 MQTT 포트(1883)에 HTTP probe(`/status`)를 보낸 프로토콜 불일치(`probe_protocol_mismatch`). 관측은 mosquitto 2.0 기본 설정의 로컬 전용 대기로 Pod IP의 1883 연결이 거부됨(`connect: connection refused`)이다. 프로토콜 차이까지 가기 전에 연결이 거부되므로, 관측으로 입증되는 결론은 `probe_port_closed`에 가깝다. 다만 HTTP probe를 MQTT 포트에 보낸 설정 결함도 사실이다. **두 라벨을 모두 정답으로 허용**하고, 관측 근거를 인용한 쪽을 우선 근거로 기록하자고 제안한다. 반영하면 #123의 RAG 없음·있음, #154 `gemma4` 비교가 바뀐다(이 사례 제외 시 RAG 없음·있음 모두 114/114).

**유지하되 기록할 점**(정답은 맞지만 이후 규칙 진단기·판정 가이드에서 다룰 것)
- `g1-my-env-miss`: CrashLoop·환경 변수 누락 로그와 함께 이전 시점의 `FailedScheduling: Insufficient cpu` 이벤트가 있다(경쟁 증거).
- `g1-sac-env-miss`: 크래시 반복의 결과로 readiness 실패 이벤트가 함께 있다.
- `g1-my-prb-proto`: 기동 초기의 연결 거부 이벤트와 이후 HTTP 응답 오류 이벤트가 섞여 있다. 프로토콜 불일치는 뒤의 이벤트로 입증된다.
- `injection-readiness-log-instruction`·`readiness-probe-port-closed`: probe 포트(8080)가 앱 포트(1883)와 달라 `probe_port_closed`가 맞다. 같은 입력에 로컬 전용 대기 로그도 있어 근거가 두 갈래다.
- `image_not_pullable` 8개: 존재하지 않는 태그(NotFound)와 레지스트리 미접속이 한 라벨로 묶인다(라벨 깊이 문제, 정답 오류는 아님).
