# Node 앱 배포·실패·진단·승인·복구 대표 시나리오 실증

## 목적 / 성공 조건
- 목적: #55 이후 추가한 요청별 기록(#95), 근거 기반 진단(#100·#117·#104), 승인 복구(#101), 에이전트 제안(#102)을 운영에서 한 흐름으로 실증해 프로젝트 전체를 설명하는 데모로 남긴다.
- 완료: 단계마다 배포 요청 ID·이미지·상태·실패 종류, 진단 결과(버전·지식 근거), 제안·승인 명령 ID, 복구 배포가 기록되고, 성공·실패·판정 불가 사례가 각각 있다. K-Le-PaaS 코드 수정과 서버 수동 패치 없이 재현된다.

## 환경과 역할 (사용자 결정)
- 운영 K-Le-PaaS, 샘플 앱 `kjhyeon0620/klepaas-sample-node`(저장소 ID 2, NodePort, #55에서 등록)만 대상. IoT 앱에는 실패를 주입하지 않는다.
- 사람(운영자): 전체 권한. 설정 변경·배포 요청은 사용자가 승인한 기존 CLI 로그인으로 에이전트가 API로 실행한다(#55와 같음). 원인 확정(`incidents confirm`)과 복구 승인(`klepaas confirm`)은 사용자가 직접 실행한다.
- 에이전트: 제안 전용(PROPOSE_ONLY) 토큰. 조회·진단·복구 계획·복구 제안만 한다(CLI `--json`). 승인·실행은 할 수 없다.
- 진단은 운영 진단 모델(OpenAI)을 실제로 호출한다(건당 약 $0.0005).

## 출발점
- 배포 #14: SUCCESS, 이미지 `sha-42b9944…`(v1), probe `/health`, env `SAMPLE_GREETING`. 설정 기록(#95)이 있어 복구 대상으로 쓸 수 있다.
- 배포 #10: #55 S6(env 누락) 실패, #95 이전이라 설정 기록·실패 종류가 없다.

## 시나리오
| 단계 | 행동 | 기대 |
|---|---|---|
| K 지식 등록 | 운영자가 샘플 앱 운영 문서를 `knowledge put` (앱 계약: 포트 8080, `/health`, 필수 env `SAMPLE_GREETING`) | 문서 rev 1, 조각 생성 |
| S1 설정 실패 | 운영자가 probe 포트를 9090으로 바꾸고 같은 이미지로 배포 | READINESS_TIMEOUT `FAILED`, 기존 Pod 계속 응답 |
| S1 진단 | 에이전트: 상세·로그·진단 | READINESS / probe_port_closed, 관측 근거 + 지식 근거 |

| S2 이미지 실패 | 운영자가 없는 태그로 배포 | IMAGE_PULL `FAILED` |

| 확인 | 이력 재조회(요청 상세의 요청 경로·명령 ID·복구 대상), 사용자 서버 `curl /version` | 끝에 v1 응답 |

- 각 단계는 앞 단계 결과가 나온 뒤 진행한다(같은 저장소 동시 배포는 409).
- 기대와 다르게 나오면 그대로 기록하고, K-Le-PaaS 결함이면 별도 이슈로 분리한다(이 이슈에서 코드를 고치지 않는다).

## 기록
- 스펙 결과 표에 단계별 배포 ID·상태·실패 종류·진단(범주/원인·버전·지식 근거 종류)·명령 ID를 남긴다. 운영 주소·토큰은 남기지 않는다.
- 원자료(JSON 응답)는 `.local/evidence/0105-end-to-end-demo/`.

### 결과 (2026-10-11, 운영)
| 단계 | 배포 | 상태 · 실패 종류 | 진단 (범주 / 원인, 버전, 지식 근거) | 제안·승인 | 복구 |
|---|---|---|---|---|---|

| S2 없는 이미지 태그 | #17 | FAILED · IMAGE_PULL | IMAGE / image_not_pullable, v2-rag, 앱 문서 + 플랫폼 이미지 runbook | 제안 명령 3 → 승인 | #18 SUCCESS |

| S4 S1 반복 | #21 | FAILED · READINESS_TIMEOUT | READINESS / probe_port_closed, v2-rag, 앱 문서 (S1 확정 사건은 인용 안 됨) | 제안 명령 4 → 승인 | #22 SUCCESS |
| S5 판정 불가 | #10 (#55 시절) | FAILED, 기록 없음 | 판단 보류, `rule` / `no-evidence-v1`, 모델 미호출. 재요청은 저장 결과 재사용 | - | - |
| 끝 | - | - | - | - | 서버 `curl /version` → `{"version":"1.0.0","greeting":"hello"}` (사용자) |

- 진단 5건(S1~S4 모델 4회, S5 규칙)이 모두 넣은 결함과 맞았다. S2는 "NotFound는 관측되나 태그 누락인지 push 전 배포인지는 확정할 수 없다"고 관측과 가설을 나눴다.
- 승인 복구 3건 모두 digest 고정 이미지(`@sha256:3e37…`)로 성공했다. #101에서 로컬 import 이미지 제약으로 확인하지 못한 digest pull 경로를 운영 GHCR에서 확인했다.
- 에이전트는 제안 전용 토큰으로 조회·진단·계획·제안만 했고, 원인 확정과 승인은 사용자가 했다. 명령 이력에 제안 사유와 결과(SUCCEEDED)가 남았다.
- 실패 단계마다 기존 Pod가 계속 응답했다(타임아웃 사유 `available=1`). IoT 앱에는 실패를 주입하지 않았다.
- K-Le-PaaS 코드 수정 0회(이 브랜치는 문서만 바꾼다), 서버 수동 패치 0회(서버 작업은 사용자 `curl` 1회).
- 진단 비용: 모델 호출 4회(약 $0.002), 문서 임베딩 1회.

### 발견한 격차 (architecture §9에 기록, #125·#126)
- 진단 응답에는 모델이 인용한 지식만 나오고 검색된 지식 목록은 남지 않는다. S4에서 S1 확정 사건이 인용되지 않았는데, 검색에서 빠졌는지(운영 기준값 0.45) 모델이 고르지 않았는지 운영에서 구분할 수 없다 (#125).
- 승인 대기 명령의 10분 만료는 승인 시점에 판정돼, 만료된 제안이 이력에 `PENDING`으로 남는다(사용자의 Codex MCP 테스트 제안, 명령 1) (#126).

## 운영 반영
- 해당 없음(실증). 끝 상태는 v1 이미지·원래 설정.

## 회고
- 어긋난 점: 반복 실패(S4)에서 확정 사건이 지식 근거로 쓰이는 것을 보이려 했으나 인용되지 않았고, 응답에 검색 결과가 없어 원인을 확인할 수 없었다. 지식 검색의 관측성을 설계(#104)에서 다루지 않았다.
- 원인 분류: 스펙 누락 — 검색 결과를 응답·이력에 남길지 정하지 않음.
- 고친 위치: architecture §9 격차로 기록하고 #125로 분리했다. 효과 측정은 #123 결과(독립 세트에서 개선 없음)를 따른다.
