# test: 로컬 모델 3개의 자연어 명령·진단 평가 (생각 끔)

## 목적 / 성공 조건
- 목적: 배포 로그와 명령을 외부로 보낼 수 없는 환경에서 로컬 모델이 운영 모델(`gpt-6-luna`)을 대신할 수 있는지, #58·#99와 같은 평가 세트와 채점으로 판단한다. 결과가 기준에 못 미치면 "채택하지 않음"도 결론이다.
- 기술적 완료: 로컬 모델 3개를 생각 끔으로 자연어 30입력 × 5회, 진단 12사례 × 10회 측정하고, `gpt-6-luna`의 기존 측정(#136·#115)과 같은 표로 기록한다.
- 운영: 기본값·운영 설정은 바꾸지 않는다. 운영 서버에는 GPU가 없다.

## 현재 동작 (2026-10-21 코드 확인)
- #150으로 `openai-compatible` 공급사와 두 하네스의 `openai-compatible:<모델>`이 있다.

- 소수 시범(2026-10-21, `gemma4:26b-a4b`, 각 1회, 원자료 `.local/evidence/0150-local-llm-pilot/`):

## 범위
- 포함:

  - 두 하네스의 동시 호출 수 `EVAL_PARALLEL` (기본 4, 로컬 측정은 1).
  - 측정: `gemma4:26b-a4b`, `qwen3.8:27b`, `qwen3.5:4b` × 생각 끔. 자연어 30 × 5회, 진단 12 × 10회.

- 제외: 기본값·운영 설정 변경, 생각 켬 전체 측정(시범으로 갈음), RAG(#123 독립 평가 세트)·임베딩, 다른 양자화·서버(llama.cpp GGUF·`mlx_lm.server`) 비교.

### 자연어 명령 (2026-10-21 15:47~19:22, #58 입력 30개 × 5회, 프롬프트 f65d4a37e6d3)
- 로컬 + Ollama(위 측정 조건). `gpt-6-luna` 행은 #136 운영 경로 재측정(동시 호출 4)을 옮겼다.
- 15:47~18:57 동안 맥이 잠들어 있어 macOS 유지보수 깨어남(약 15분 간격) 동안에만 진행됐다. 지연은 호출 앞뒤 실제 시각으로 재므로, 잠자기에 걸친 호출이 있으면 그 값이 커진다. `gemma4` 전체와 `qwen3.8` 일부가 이 구간이다. 정확도에는 영향이 없다.

- 세 모델 모두 확인 없이 변경 실행 해석 0. 변경 intent는 모델과 무관하게 승인 대상이라는 구조(#58, ADR-0002)가 그대로 성립했다.
- `gpt-6-luna`의 과대 9는 위험·악의 입력을 변경 intent로 해석해 승인 요청을 만든 경우다. `gemma4`는 이런 해석이 0이었다.
- `qwen3.8:27b`: 과대 4는 `adversarial-scale-all-to-zero`·`adversarial-unrestricted-scale-all-en`, 변경 intent 날조 1은 `adversarial-other-team-app`(다른 팀 앱 대상)에서 났다.
- `qwen3.5:4b`: 날조가 모호·악의 입력 전반(대상·숫자 누락, 다른 팀 앱)에 퍼져 있고, `normal-rollback-commit`에서 저장소·소유자·커밋에 아주 긴 숫자를 지어냈다(첫 측정의 채점 오류를 일으킨 값과 같은 유형).
- 지연은 판정에 넣지 않았다. `gemma4`는 `gpt-6-luna`의 약 1.5배다.

### 결론
- **`gemma4:26b-a4b`(생각 끔)는 두 평가를 모두 통과했다.** 자연어 intent 100%, 진단 구체 원인 100/100으로 `gpt-6-luna`와 같거나 높고, 지연은 1.5~2.3배다. 외부로 데이터를 보낼 수 없는 환경에서 `openai-compatible` 설정만으로 대체할 수 있는 후보다.
- 다만 이 평가 세트는 이미 포화에 가깝다(#100: 저가 모델도 거의 만점, `gpt-6-luna`도 99%대). 로그에 원인이 드러난 사례가 많고 라벨 목록에서 고르는 문제다. "gemma가 더 정확하다"가 아니라 "이 난이도에서는 로컬 MoE 모델로 충분하다"로 읽는다. 더 어려운 독립 평가(#123 blind-test 39사례)는 후속 이슈로 확인한다.
- `qwen3.8:27b`는 약 6배 느리면서 진단 품질이 낮고 변경 intent 날조가 있어 이 용도에 이점이 없다. `qwen3.5:4b`는 진단 판단 보류와 자연어 날조가 기준에 크게 못 미쳐, GPU 없는 CPU 서버에서 돌릴 수 있는 크기로는 대체가 안 된다.
- 운영 기본값은 바꾸지 않는다. 운영 서버에는 GPU가 없다.

## 운영 반영
- 없음 (테스트·문서만 변경).

## 회고
- 어긋난 점: (1) 자연어 첫 측정이 채점기의 `Integer.parseInt` 예외로 30분치 결과 없이 끝났다. 하네스가 모든 모델을 마친 뒤에야 결과 파일을 써서, 한 호출의 채점 예외가 전체를 잃게 했다. (2) 잠든 맥에서 측정을 다시 시작해 `caffeinate -i`(유휴 잠자기만 막음)가 소용없었고, 약 3시간 동안 유지보수 깨어남 구간에만 진행됐다. (3) Ollama 기본 컨텍스트(32K)를 그대로 써서 `qwen3.8`이 26GB를 차지해 스왑이 생겼다(입력은 최대 2.7K토큰).
- 원인 분류: 테스트 부재(모델이 만든 극단 값으로 채점기를 시험한 적 없음), 외부 제약 미인지(macOS 잠자기·Ollama 기본값).
- 고친 위치: `NlpEval.mentionsNumber`를 두 자리 숫자까지만 낱말 비교하도록 고치고 회귀 테스트 추가. 장시간 로컬 측정 조건(깨어 있는 상태에서 시작, 잠자기 방지는 시스템 잠자기까지 막는 옵션, 컨텍스트 8K)은 후속 측정 스펙에 적는다.
