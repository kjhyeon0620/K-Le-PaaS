# Spec-Driven Development 절차

이 문서는 이슈를 **스펙 → 구현 → 검증 → 회고** 순서로 진행하는 절차의 단일 기준(SSOT)이다.
사람과 모든 AI 도구(Claude, Codex, Gemini 등)가 같은 절차를 따른다.

## 1. 원칙

- 구현 전에 **목적, 범위, 계약, 예외, 완료 증거**를 확정한다. 모호한 상태로 코드부터 쓰지 않는다.
- 대화에서 내린 결정은 채팅에만 남기지 않고 이 저장소의 문서로 남긴다.
- 스펙은 이슈 하나당 하나를 둔다. 공통 규칙은 공통 문서에 한 번만 쓰고, 스펙에서는 링크로 참조한다.
- 절차의 무게는 이슈 크기에 맞춘다.
- 공개 저장소다. 비밀값, 운영 호스트, 개인 인벤토리 정보는 스펙에 쓰지 않는다. 운영 검증 원자료는 `.local/evidence/`에 두고, 스펙에는 결과 요약만 적는다.

## 2. 문서 계층

| 계층 | 문서 | 답하는 질문 |
|---|---|---|
| 제품 | [`docs/product.md`](../product.md) | 무엇을 왜 만들고, 어떤 순서로 진행하는가? |
| 구조 | [`docs/architecture.md`](../architecture.md) | 책임을 어떻게 나누고, 공통 계약과 알려진 격차는 무엇인가? |
| 결정 | [`docs/adr/`](../adr/README.md) | 이 결정을 왜 내렸고, 무엇을 포기했는가? |
| 운영 | [`docs/CICD.md`](../CICD.md), [`docs/ORACLE_K3S_GHCR_DEPLOYMENT.md`](../ORACLE_K3S_GHCR_DEPLOYMENT.md), [`docs/STAGE2_RESOURCE_ACCESS.md`](../STAGE2_RESOURCE_ACCESS.md) | 어떻게 배포하고 운영하는가? |
| CLI | [`docs/CLI_REFERENCE.md`](../CLI_REFERENCE.md), [`docs/CLI_STRATEGY.md`](../CLI_STRATEGY.md) | CLI 계약과 방향은 무엇인가? |
| 작업 규칙 | [`AGENTS.md`](../../AGENTS.md) | AI는 어떤 규칙으로 작업하는가? |
| 이슈 | `docs/specs/NNNN-<slug>/spec.md` | 이번 이슈에서 무엇을 바꾸고, 어떻게 증명하는가? |

## 3. 이슈 등급

| 등급 | 기준 | 산출물 |
|---|---|---|
| **S** | 오타, 단순 버그, 설정 한 줄, 문서만 수정 | 스펙 없음. GitHub 이슈 본문(배경, 작업, 완료 조건)만 작성 |
| **M** | API 하나, 화면 하나, 한 모듈 안의 변경 | `spec.md` (Tasks 섹션 생략) |
| **L** | backend·frontend·CLI에 걸친 변경, 스키마 변경, 권한·승인 경계 변경, 운영 반영 절차가 필요한 변경 | `spec.md` + Tasks 섹션 |

다음 중 하나라도 해당하면 최소 M 등급으로 본다.
- Flyway 마이그레이션 추가
- 권한(토큰 scope, 소유권, 허용 참조) 변경
- 위험도 분류나 명령 승인 흐름 변경
- 배포 상태 판정 변경
- API, CLI 출력, exit code 계약 변경

## 4. 경로와 이름

- 이슈가 있는 스펙: `docs/specs/<4자리 이슈 번호>-<브랜치 slug>/spec.md`
  - 예: `feat/#51-app-probes-resources` → `docs/specs/0051-app-probes-resources/spec.md`
- 이슈를 만들기 전의 초안: `docs/specs/draft-<slug>/spec.md` (`issue: TBD`). 이슈를 만들면 폴더 이름을 바꾼다.
- 템플릿: [`_template.md`](_template.md)

## 5. 진행 흐름

```text
① 의도 작성: 사용자가 한두 줄로 무엇을 원하는지 적는다
      ↓
② 초안 작성: AI가 product/architecture/ADR/관련 코드를 읽고 등급을 제안한 뒤 spec 초안을 쓴다
      ↓
③ 질문: 구현자가 임의로 정해야 하는 부분만 골라 묻는다 (한 번에 최대 5개)
      ↓
④ 결정 기록: 답을 Decisions에 기록한다. 여러 이슈에 영향을 주는 결정은 ADR이나 architecture로 옮긴다
      ↓
⑤ ready: Open 질문이 0개가 되면 status: ready로 바꾼다
   AI가 이슈를 만들고(열린 이슈가 있으면 재사용) 브랜치를 만든다
      ↓
⑥ 구현: status: in-progress. 가능하면 테스트를 먼저 쓴다. 스펙이 바뀌면 "구현 중 스펙 변경" 기준을 따른다
      ↓
⑦ 검증과 회고: 완료 증거(스키마 변경이면 운영 DB 사본 검증 포함)를 실행하고 회고(7장)를 쓴 뒤 status: done으로 바꾼다
      ↓
⑧ 보고와 PR: 커밋하지 않은 상태로 작업 요약을 보고한다
   승인을 받으면 AI가 커밋, 푸시, PR 생성까지 한다. 머지는 사용자가 한다 (머지 = 완료)
      ↓
⑨ 운영 반영: 머지 후 main 배포 workflow 결과와 운영 반영(마이그레이션 버전 등)은
   다음 이슈 PR에서 해당 스펙의 `운영 반영`에 기록한다. 배포가 실패하면 새 fix 이슈로 다룬다
```

### 상태값

| status | 의미 |
|---|---|
| `draft` | 작성 중이거나 Open 질문이 남아 있음 |
| `ready` | 결정이 끝나 구현을 시작할 수 있음 |
| `in-progress` | 이슈 브랜치에서 구현 중 |
| `done` | 구현과 검증, 회고가 끝남. 구현 PR 안에서 바꾸고 머지로 확정한다 |
| `dropped` | 진행하지 않기로 함. 이유를 Decisions에 남긴다 |

### 질문 규칙

- 분량을 늘리기 위한 질문이 아니라 **아직 내리지 않은 결정**을 찾는 질문만 한다.
- 이 프로젝트에서 특히 확인할 것:
  - **권한**: 어떤 토큰 scope(`READ_ONLY`/`PROPOSE_ONLY`/`DEPLOY`/`FULL`)와 소유권 검사를 거치는가? 권한이 없는 경로에서 Kubernetes 호출이 0회인가?
  - **위험도와 승인**: 새 동작의 위험도는 무엇인가? 승인 후 실행 대상이 바뀔 수 있는가?
  - **중복과 동시성**: 같은 요청이 재전송되거나 동시에 들어오면 어떻게 되는가? (delivery ID, idempotency, 원자적 상태 전이)
  - **실제 상태와 추정**: 표시하는 값이 실제 관측값인가, 저장값인가, 추정값인가? 판단할 수 없으면 무엇을 표시하는가(`UNKNOWN`)?
  - **실패와 복구**: 실패를 성공으로 기록할 여지가 없는가? 앱 롤백과 DB·Secret 복구를 구분했는가?
  - **스키마**: 마이그레이션이 이전 릴리스와 호환되는가? 기존 행의 기본값은 무엇인가?
  - **비밀값**: 응답, 로그, 문서, 스펙에 비밀값이 남지 않는가? (Secret은 이름만 다룬다)
  - **경계 계약**: API 응답(snake_case), CLI `--json` 출력, exit code가 바뀌는가?
- 코드나 기존 문서를 읽으면 답이 나오는 것은 묻지 않고 직접 확인한다.
- 합리적인 기본값이 있으면 질문하지 않고 "기본값 X로 가정" 형식으로 Decisions에 적는다. 사용자는 검토할 때 이를 뒤집을 수 있다.

### 구현 재량과 범위 변경

| 구현 재량 (AI가 결정) | 범위 변경 (spec을 고친 뒤 진행) |
|---|---|
| 내부 메서드 구조, 이름 | 새 endpoint, 새 CLI 명령·옵션, 새 화면 |
| 계약 안에서의 리팩토링 | 응답 필드, 에러 코드, exit code 변경 |
| 테스트 헬퍼 추가 | Flyway 마이그레이션, 새 설정 키, 기본값 변경 |
| 로그 문구 (비밀값 제외) | 위험도, 승인, 토큰 scope, 소유권 규칙 변경 |

### 구현 중 스펙 변경

구현하다 스펙과 다른 사실이나 새 결정이 필요해지면 아래 기준으로 처리한다. 어느 경우든 스펙을 먼저 고치고 코드는 그 뒤에 맞춘다.

| 변경 종류 | 처리 |
|---|---|
| 사실 정정(코드·외부 시스템 동작이 스펙의 전제와 다름), 구현 재량 안의 결정, 새로 발견한 예외·경계 상황, 완료 증거 보강 | **AI가 스펙을 바로 고치고 계속 진행**한다. Decisions에 `YYYY-MM-DD (구현 중) 내용 → 결정. (이유)`로 남기고, 커밋 전 보고의 "스펙 상태"에 포함한다 |
| 범위 변경 (위 표의 오른쪽 열, 제외 범위 해제, 새 기능) | **AI가 스펙 수정안을 쓰고 해당 항목을 Open 질문으로 올린 뒤 사용자에게 묻고 기다린다.** 답을 받으면 Decisions로 옮긴다. 기다리는 동안 영향받지 않는 부분은 계속 작업할 수 있다 |
| 이번 범위 밖에서 발견한 결함·개선 | 스펙에 "범위 밖, 별도 이슈"로 기록하고 이슈 후보로 보고한다. 이슈 생성은 각 저장소의 GitHub 정책을 따른다 |

- 스펙을 바꿨다고 이전 결정을 지우지 않는다. 뒤집힌 결정은 취소선이나 "→ YYYY-MM-DD 변경" 표시로 남긴다.
- `status: done`은 **구현 PR 안에서** 바꾼다. 머지 후 status만 바꾸기 위한 별도 커밋·PR은 만들지 않는다.
- 배포 workflow 결과와 운영 반영처럼 머지 후에야 알 수 있는 정보는 **다음 이슈 PR에서** 해당 스펙의 `운영 반영`에 기록한다.
- `status: done`인 스펙은 회고와 운영 반영 기록 외에는 고치지 않는다. 머지 후 바뀌는 동작은 새 이슈와 새 스펙으로 다룬다.

## 6. 문서 동기화 (완료 조건)

코드를 변경하면서 아래 문서를 함께 고치지 않으면 완료로 보지 않는다.

| 변경 종류 | 함께 수정할 문서 |
|---|---|
| 상태 모델, 위험도, 권한, 에러 코드, 설정 키, 모듈 책임 | `docs/architecture.md` |
| 되돌리기 비싼 기술 결정 | `docs/adr/NNNN-*.md` 새로 작성 또는 기존 ADR의 Status 갱신 |
| 백엔드 API | `backend/README.md` (주요 API 목록), Springdoc 어노테이션 |
| CLI 명령, 출력, exit code | `docs/CLI_REFERENCE.md` |
| 사용자 앱 배포 방식 (이미지, probe, 도메인, 토큰) | `docs/ORACLE_K3S_GHCR_DEPLOYMENT.md` |
| 플랫폼 배포, 스키마 마이그레이션 절차 | `docs/CICD.md` |
| 리소스 접근, 허용 참조 | `docs/STAGE2_RESOURCE_ACCESS.md` |
| 기능 구현 상태 표 | `README.md` 현재 상태 표, `backend/README.md`, `frontend/README.md` |
| 범위, 실행 순서, 이슈 상태 | `docs/product.md` |

## 7. 회고

이슈를 마칠 때 spec의 `회고` 섹션을 채운다.

| 원인 | 고칠 위치 |
|---|---|
| 동작을 정해 두지 않았음 | spec 템플릿의 질문 항목, `product.md` |
| 공통 구조가 없었음 | `architecture.md`와 공통 코드 |
| 규칙은 있었지만 AI에게 전달되지 않았음 | `AGENTS.md`, 이 문서 |
| 틀렸는데 검사하지 않았음 | 테스트 |
| 완료 판단이 느슨했음 | spec의 `완료 증거` 기준 (로컬, 운영 DB 사본, 실제 클러스터를 구분했는가) |

- "앞으로 주의한다" 같은 문장을 추가하기보다 **테스트, 공통 함수, CI 검사로 바꾸는 것**을 먼저 검토한다.
- 한 번 일어난 사소한 실수 때문에 검증 장치를 새로 만들지 않는다. 반복될 가능성이 높고 영향이 클 때만 만든다.
