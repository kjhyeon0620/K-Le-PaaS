# 진단 평가 데이터셋 설명서

배포 실패 AI 진단의 오프라인 평가 자료. 정답 기준은 [평가 명세](../../../../../docs/eval/diagnosis-eval-spec.md), 버전은 `manifest.json`, 변경은 [CHANGELOG](CHANGELOG.md).

## 구성 (1.0.0)
| 분할 | 사례 | 갈래 | 출처 |
|---|---|---|---|
| `dev` | 51 | SUPPORTED 49, INSUFFICIENT 2 | #99: 로컬 k3s 실제 캡처 8 + 캡처 가공 4(증거 제거 2, 로그 속 지시문 2). #123: 다른 계열 모델(Gemini)이 목적을 모른 채 쓴 시나리오를 로컬 k3s에서 재현한 39(공개 이미지 25, 사내 서비스 14) |
| `robustness` | 24 | ROBUSTNESS 20, INSUFFICIENT 3, CONFLICT 1(자동 채점 제외) | #158: #99 사례의 기계 변형(미끼, Pod·로그 추가, 증거 제거) |
| `test` | 0 | - | 다음 이슈에서 신규 주입으로 채우고 동결한다 |

- 구체 원인 6개(이미지 참조 형식, 이미지 받기 실패, CPU 부족 스케줄 실패, 필수 env 누락, probe 포트 닫힘, probe 프로토콜 불일치)와 판단 보류만 다룬다.
- 입력은 플랫폼의 상세·로그 API 응답이다. env 값은 없고 이름만 있다. 로그는 Pod당 최대 40줄.

## 만든 방법
- 캡처: 패키징 JAR + PostgreSQL + Docker 임시 단일 노드 k3s v1.30.6(로컬 ARM64 맥). 기준 설정으로 성공 배포 → 설정 변경 → 실패 배포의 응답을 저장. 공개 이미지는 로컬에 있던 것을 썼다.
- #123 사내 서비스는 생성된 명세대로 셸 스크립트 이미지(`FROM redis:7-alpine`, busybox `nc`)로 구현했다(시스템 쪽이 기계적 규칙으로 구현).
- 정답: #99는 시스템을 만든 쪽(Claude Code)이 붙였고, #123은 시나리오 작성 모델이 붙인 라벨이다. 2026-10-22 1차 감사(Claude Code)에서 1건을 복수 정답으로 정정했다. 근거 묶음은 판정 가이드를 기계적으로 적용해 정했다(1건 수동).
- 정답 일치도(다른 모델·사람 재판정)는 `dev`에서 재지 않았다.

## 알려진 편향과 한계
- 단일 노드 로컬 k3s, 공개 이미지 위주(redis·postgres·mysql·mosquitto·influxdb), 개인 서버 앱 규모. 기업 장애 분포를 대표하지 않는다.
- 모든 지원 사례가 한 줄 시그니처(이벤트·상태·로그 한 줄)로 원인이 드러난다. 시그니처 규칙이 지원 사례 48/49를 맞힌다(#161).
- `dev`는 프롬프트·규칙을 만들 때 여러 번 본 사례다. 처음 보는 장애의 성능 근거가 아니다.
- 시나리오의 일부는 LLM이 설계했고 실제 운영 장애가 아니다.

## 다루지 않는 범위
OOMKilled·아키텍처 불일치·느린 기동 같은 분류 밖·경계 장애(다음 이슈의 `test`에서 일부 추가), ConfigMap·Secret 참조, pull secret, 네트워크 정책·DNS, 여러 컨테이너 Pod, 노드 장애, 운영에서 확정한 실제 장애.
